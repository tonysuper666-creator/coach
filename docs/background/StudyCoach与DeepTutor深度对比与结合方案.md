# StudyCoach × DeepTutor：深度对比与结合方案（2026-10-29）

依据：两路只读调研（StudyCoach 归档仓库的源码与文档；DeepTutor 1.6.15 的后端源码与前端构建物），加上我自己抽查的几处。带 [未证实] 的是推断，没有实机验证。

## 一、一句话判断

- **StudyCoach 有“闭环的产品”，没有“能用的引擎”**：它把“今天做什么 → 学 → 练 → 批 → 掌握 → 复习 → 日记”做成一条线、一个入口；但它的 Web 版没接上 AI，完整闭环只存在于被冻结的桌面版里。
- **DeepTutor 有“强大的引擎”，没有“闭环的产品”**：同一个引擎（`/ws` + 同一个 `TurnRequest`）撑着聊天、精通会话、阅读、课程，工具和模型接入都很成熟；但**入口是并列的，上下文靠你每次手动选**，所以割裂。
- **所以结合的方向很清楚**：用 DeepTutor 当引擎，用 StudyCoach 当“产品形态 + 学习规则 + 设计语言”，中间加一层很薄的“编排层”，把“选资源”这件事从用户手里拿走。

## 二、概念模型对照

| 维度 | StudyCoach | DeepTutor |
|---|---|---|
| 中心对象 | 课程版本（不可变，改动就生成 N+1）→ 能力 → 单元 → 内容块 | 课程只是引用集合；真正的学习单位是“精通路径 → 知识点”，路径不属于课程 |
| 状态来源 | 追加式事件账本，所有状态（位置、掌握度、复习队列、日记）都是对事件的纯函数投影 | 路径整体存成 JSON，再加事件表和证据表；会话属于课程/路径的关系写在 `sessions.preferences` 的 JSON 里，不是外键，两个数据库之间也没有外键 |
| 入口 | **一个“今天”**，唯一主动作是“继续当前小课”，复习和日记是次级卡 | 主页聊天、课程聊天、精通会话、阅读会话、书、写作、伙伴……并列 |
| 上下文绑定 | 单元自带资料块、能力、证据规则，自动绑定 | 精通路径和阅读会话自动绑定；课程只带知识库、人设和约定；**笔记本、历史、题库、记忆默认“仅本轮”，要你手动点** |
| 资料引用 | 每个解释性断言都要带来源归属（四类），代码层校验必须在本次提供的来源范围内 | 备课时由 `mastery_prepare_lesson` 取原文证据并校验引文页码，其余靠提示词约束 |
| AI 边界 | 一个执行入口，物理调用预算硬上限 2 次，高风险内容（出题、批改、状态改变）独立复核，不确定则绝不写入掌握 | 工具丰富；答案和解析登记在服务端，选择题精确匹配，概念类由服务端评估；模型自己宣布的 `passed` 被忽略 |
| 前端 | React 19 + 令牌化设计系统，暖纸色/粉色/衬线标题 | Next.js，功能多、风格通用 |

## 三、学习闭环逐步对照

| 步骤 | StudyCoach（桌面版为准） | DeepTutor（我们现在） |
|---|---|---|
| 导入资料 | 上传 → 提取 → 审查来源 → 规划路线 → 原子发布 | 我们用脚本生成课程库、阅读集、笔记本、108 题、复习书（一次性） |
| 今天做什么 | 首页唯一主按钮；位置来自“续接”，不是算法推荐 | 要自己点进精通路径的“下一个”；主页聊天不知道你学到哪 |
| 讲解 | 九种教学模式（直觉、正式、考试写法、换例子、地图、短诊断、费曼复述……）集中注册 | 导师自由发挥；有模式（outline/study/review）但不是讲法 |
| 追问 | 右栏追问，**只记录，不改掌握度**，只取当前单元最近 12 轮 | 同一对话里随意追问，精通会话内会被教学流程打断/混合 |
| 练习批改 | 三级渐进提示；批改按固定 rubric，每条给分必须引用学生原答的逐字片段；独立复核 | 选择题精确匹配；其余语义评估，置信度低于 0.8 记为未判 |
| 掌握度 | 只认**首次独立**、得分≥0.8、提示<3、用途为闭卷推导/未见变体/限时/模考的作答；重复题、重试、阅读都不算 | 最近 5 次加权正确率 ≥0.9 即过；我们又把定性门改成了选择题门（选择题即可过关） |
| 复习 | 复习页先只读队列，点开始才出题；结果只改复习安排，不计掌握 | 精通有按知识点的复习；练习题库另有一套按题的复习，**两套互不相通** |
| 日记 | 每个自然日一篇：AI 摘要区 + 人工区 | 有学习日志，没有“每天一篇”的产品形态 |
| 阶段 | 定向 → 通读 → 深攻 → 模考 → 修复，时间不推进阶段，必须带证据 | 没有阶段概念 |

**两个值得注意的差异：**
1. **我们放宽的“选择题即过关”，在 StudyCoach 的标准下只算较弱的证据。** 这对“期中冲刺”合理，但如果以后想区分“应付过关”和“真正掌握”，要有第二层标准（见方案里的“证据分层”）。
2. **DeepTutor 选“下一个目标”时不看前置依赖**（我抽查 `policy.py`：`prerequisite_ids` 只在序列化时出现，没参与选择）。StudyCoach 有前置能力图，未掌握前置则下游锁定。

## 四、DeepTutor 的割裂到底出在哪

两路调研交叉印证后，我把根因归成四条：

1. **对话不属于任何学习对象。** 主页聊天没有 `mastery_*` 教学工具，不写租约、不动掌握度；它也不知道你学到哪个知识点。想问“NPV 怎么算”的随口一问，和你正在学 NPV 的那个知识点没有关系。
2. **上下文要手动选。** 课程只带知识库/人设/约定，不带笔记本、阅读集、题库；“每轮附带”这类开关是前端状态，默认多是“仅本轮”。所以“起新对话”和“在对话里选笔记本”才会同时存在，这正是你说的两边割裂。
3. **掌握度只在精通会话里写。** 其他入口产生的作答（阅读、题库、笔记本）只追加证据并重排复习，不改掌握度，而且需要显式带路径和知识点 id，我没找到前端自动带的地方。
4. **两套复习互不相通。** 精通的复习按知识点，题库的复习按题，代码里后者没有任何 mastery 引用。我抽查我们的库：练习导入记录只有 1 条，题库复习状态 0 条——我们的 108 道题实际上没进入过复习流程，这就是割裂的现实后果。

其他次要的：课程“交接”只是一张卡片、一条路径同一时间只能有一个对话在教（租约）、记忆没有“精通/阅读”这一面、选了导师那一轮部分工具会被剔除。

StudyCoach 没有这些问题，不是因为它更聪明，而是因为它只有一条线：对象是“课程版本里的单元”，对话天然属于“当前单元”，状态来自同一本账。

## 五、各自不可替代的东西

**DeepTutor 要留的（引擎）**：
- 掌握度状态机、证据校验（答案服务端登记，模型无法自称通过）、事务 + 事件日志 + 租约（可断点重放）；
- 订阅模型接入（我们的桥）、真流式、四位 CLI 导师、检索与原文页视图；
- 已有内容：49 个知识点的大纲、课程库、阅读集、题库、笔记本。

**StudyCoach 要借的（产品与规则）**：
- 导航与形态：今天 / 路线 / 复习 / 记录 / 资料 五项，首页单一主动作；
- 学习规则：证据资格分层、前置依赖、复习先看队列后出题、追问不改掌握、阶段需要证据；
- 日记：每天一篇，AI 摘要 + 人工区；
- 设计语言：令牌（暖纸 `#f4efe6`、粉色主色、衬线标题、大圆角、120–320ms 动效、暗色主题、对比度契约）；
- AI 边界：来源归属校验、逐字证据批改（可作为 DeepTutor 批改的“复核层”）。

**不借的**：StudyCoach 的 Rust 持久层、Tauri 壳、托管网关、Postgres 服务群、事件账本全套治理（对新应用偏重，复活成本远高于收益）。

## 六、结合方案：一层很薄的“编排层”（Coach Gateway）

**原则**：不合并两个代码库；DeepTutor 继续做引擎，我们新增一个很小的服务，放在现在手机入口（3790）的位置，对外只暴露“学习”这一件事。

```
手机/平板/电脑：StudyCoach 风格前端（五个入口）
                    │
            Coach Gateway（新，约 1–2 千行）
   ├ 今天：聚合“下一个知识点 + 到期复习 + 今日日记”
   ├ 对话：永远属于一个“学习对象”，网关替用户组装全部绑定
   ├ 复习：把精通复习与题库复习合成一个队列（读聚合，写回各自）
   ├ 日记：每日一篇（AI 摘要 + 人工区）
   └ 证据分层：展示“已通过 / 稳固”两档
                    │  复用 DeepTutor 的 /ws turn 协议、mastery REST、事件回放
            DeepTutor 引擎（不动）
```

### 关键机制

1. **对话属于对象，不再“起新对话”。**
   对话分三种，都由网关创建并自动绑定，用户永远不需要选笔记本、阅读集、题库：
   - **知识点学习**：绑定课程 + 路径 + 当前知识点 + 该知识点的来源页码 + 相关笔记 + 题库中同知识点的题；走完整的 `mastery_*` 流程。
   - **随口问**：在“今天”里一个输入框，绑定课程 + 当前知识点（只读），带课程资源，不动掌握度；可一键“存为笔记”或“加入复习”。
   - **复习**：先看只读队列，点开始才出题；结果只改复习安排。
2. **统一“今天”页**：唯一主按钮 = 继续当前知识点；旁边“到期复习 N 个”“今日日记”。取代“在精通目标里找到下一个”。
3. **补三条缝**：
   - 把非精通来源的作答，用显式的 `mastery_path_id + knowledge_point_id` 写成证据（DeepTutor 支持追加证据，不改掌握度）；
   - 合并两套复习为一个队列的只读聚合；
   - 选“下一个目标”时由网关加上前置依赖过滤（我们的大纲已有 `prerequisite_ids` 字段，目前为空，需要补）。
4. **证据分层（展示层，不动引擎）**：“已通过”= 选择题达标（现状）；“稳固”= 满足 StudyCoach 的资格（首次独立、≥0.8、提示<3、闭卷或未见变体）。这样既保留我们为冲刺放宽的门，又不丢掉“真掌握”的刻度。
5. **日记**：用 DeepTutor 已有的学习日志与事件作为原料，每天生成一篇摘要，旁边留人工区。

### 前端

- 技术：React + 现成的 StudyCoach 设计令牌 + KaTeX 渲染公式 + 之前做好的折叠屏自动布局（按窗口宽度选布局）。
- 范围只含：今天、路线（含大纲）、学习会话、复习、记录；设置、伙伴、看板、写作等都不做。
- 仍放进现有安卓壳；是否做真原生见 `原生应用评估.md`。

## 七、分期与估算（我带 AI 协助、一个人）

| 期 | 做什么 | 估算 | 备注 |
|---|---|---|---|
| P0 | **期中前不动架构**（你 11-02 考试） | 0 | 可选：只在现有页面上换 StudyCoach 配色，半天 |
| P1 | Gateway 最小版：“今天”页 + 对话自动绑定（知识点学习/随口问）+ 只读复习队列 | 4–6 天 | 立刻消除“起新对话 / 手选笔记本”的割裂 |
| P2 | 统一复习队列（含题库）+ 证据写回 + 前置依赖 + 日记 | 4–6 天 | 需要补大纲前置依赖数据 |
| P3 | 完整 StudyCoach 风格前端 + 折叠屏四形态打磨 + 公式/流式细节 | 1–1.5 周 | 可与 P2 并行一部分 |
| P4 | 可选：原生 Compose 或通知、小组件 | 视需要 | 见原生评估 |

## 八、风险与取舍

- **协议依赖**：网关要依赖 DeepTutor 的 `TurnRequest` 字段和 `tool_result.metadata` 里的卡片键（`mastery_question`、`mastery_grade`、`mastery_handoff`、`course_handoff`）。`TurnRequest` 是 `extra="forbid"`，升级后字段一变，旧客户端会被拒。缓解：网关集中处理，所有协议细节只在一处，加一个启动自检。
- **租约**：一条路径同一时间只允许一个对话在教，网关需要管理（切换对象时先放租约）。
- **精通 REST/WS 的返回很多是无模型的字典**，不如 turn 协议稳定。
- **证据分层是展示层**：真正的掌握度仍由 DeepTutor 写；如果以后想让“稳固”影响调度，就要动引擎，难度会上升。
- **决策风险**：如果把网关设为唯一入口，原界面就退为后台管理；需要确认你接受。

## 九、仍未证实的点

1. “每轮附带”开关刷新后是否保留；
2. 我们 108 题的实际导入方式（导入记录只有 1 条，复习状态 0 条）；
3. 阅读、书页是否在前端给作答带上路径与知识点关联；
4. 记忆归并是否有自动触发；
5. 选了导师时实际挂载的工具集（只由代码推导）；
6. `/openapi.json` 是否可用；
7. StudyCoach 的 `course-builder`、`source-extractor` 能否脱离其他包单独编译。

## 十、需要你拍板的三件事

1. **入口**：接受 Gateway 作为唯一入口（DeepTutor 原界面退为后台）吗？
2. **范围**：P1 先只做“今天 + 知识点学习 + 随口问”，复习和日记放 P2，可以吗？
3. **时机**：期中前完全不动，期中后（11-03 起）开工，可以吗？
