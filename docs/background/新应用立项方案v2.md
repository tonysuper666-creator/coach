# 新应用立项方案 v2：带 Multica 团队从 0 做「StudyCoach × DeepTutor」（桌面 + 安卓原生）

状态：**待你拍板 4 件事（见第九节）后才创建 Multica 卡片、启动 agent**。在此之前不花额度、不动 DeepTutor（期中前它必须保持稳定）。
代号暂用「Coach」，名字由你定。

## 一、产品定义（一句话）

**一个学习闭环、一个入口、一个对象模型，AI 导师的能力不打折。**
把 StudyCoach 的「今天 → 学 → 练 → 批 → 掌握 → 复习 → 日记」闭环和严格的证据规则，与 DeepTutor 的导师能力（工具化教学、原文检索、多导师、流式、可重放事件）合在一起，重新写成一个我们自己掌控的应用。

和上一版方案（给 DeepTutor 加网关）的区别：不再依赖 DeepTutor 的内部协议和 6 处补丁，也不再被它的数据模型限制；代价是工作量从「周」变成「月」。

## 二、从两边总结出的设计原则

**从 DeepTutor 学到的（要避免）**
1. 对话不属于任何学习对象 → 在 Coach 里，**每个对话都挂在一个学习对象上**（知识点 / 复习项 / 课程），不存在“起新对话再手选资源”。
2. 掌握度只在特定会话里写、复习两套互不相通 → **一本事件账本，所有状态都是它的投影**。
3. 内部协议不稳、靠补丁 → 协议由我们自己定义并版本化。

**从 StudyCoach 学到的（要避免）**
1. 治理过重：26 项长期契约、十几个自定义门禁、台账里过期未处理的债，把一个人的工具拖成了企业项目 → 遵守你已定的理念：**限制只为保护用户，代码量、行数、门禁数只报告不设卡**；测试只测用户感知到的质量。
2. Web 版 AI 没接上、评分器是占位模板 → **AI 链路从第一天就是真的**，不留“确定性占位”冒充完成。
3. 依赖个人 VPS、托管网关、OAuth → 起步只依赖这台 Mac 和订阅 CLI。

**要保留的核心规则（来自 StudyCoach，已读过源码）**
- 证据资格：首次独立作答、得分 ≥0.8、提示少于 3 次、闭卷/未见变体/限时/模考才算掌握；重复题、重试、阅读不算；资格判断 fail closed。
- 追问只记录，不改掌握度；复习先看只读队列、点开始才出题，结果只改复习安排。
- 批改必须引用学生原答的逐字片段，rubric 不可被模型改动；出题、批改、状态改变要独立复核，不确定则不写入掌握。
- 阶段推进需要证据而不是时间；双轨分（首做/修复）永不合并。
- 设计语言：暖纸色底、粉色主色、衬线标题、大圆角、克制动效、暗色主题。

**要保留的能力（来自 DeepTutor）**
- 工具化教学流程（备课取原文证据 → 讲 → 出题 → 判分 → 更新）、选择题服务端精确判分、概念题服务端评估。
- 原文检索与页码引用（教材每页带「PDF 页 / 书页」标记）。
- 多位导师（Claude / Codex / Grok / Antigravity）与兜底链；真流式；订阅 CLI 接入（无需 API Key）。
- 事务 + 事件回放 + 租约思路（一个知识点同时只让一个对话在教）。

## 三、系统架构（我的推荐，等你定技术栈）

```
Android 原生 App ─┐                         ┌─ AI 适配层（订阅 CLI：Claude/Codex/Grok/Antigravity，流式 + 兜底）
macOS 桌面 App ───┼─ HTTPS/WS (Tailscale) ─ Coach Server ─┼─ 事件账本 + 内容库（SQLite，FTS5 检索）
Windows 桌面 App ─┘     离线缓存 + 作答队列   (Mac 上常驻) └─ 教学编排（备课/讲/出题/批改/复核/日记）

共享：coach-domain（纯逻辑：事件、投影、证据策略、复习调度、阶段、前置图）
      —— 服务端与所有客户端用同一份代码
```

- **推荐栈：Kotlin Multiplatform + Compose Multiplatform。** 一份界面和领域代码同时产出安卓原生、macOS、Windows；服务端用同一语言（Ktor），领域规则不用写两遍。折叠屏的窗口尺寸类、列表-详情面板都有官方支持。
- **AI 适配层第一版直接复用我们现成的订阅桥**（已有真流式、兜底、四家 CLI），Kotlin 服务端通过它调用；稳定后再决定是否改写成 Kotlin。
- **服务端放这台 Mac**：安卓和 Windows 通过 Tailscale 连；Mac 桌面端同机直连。设计成可迁移，将来想搬到常驻机器只是换地址。
- **数据迁移**：写一个一次性工具，把现有课程库、49 个知识点大纲、108 道题、笔记本、已有掌握记录导入新账本，学习不中断。
- **公式渲染**是最大技术风险：Compose 没有现成 LaTeX，先用小 WebView + KaTeX 做验证，作为第一批 spike。

## 六、M0 的卡片草案（等你拍板后才创建）

1. 立项 ADR：技术栈、服务端位置、数据模型、协议版本策略（Architect）。
2. Spike A：Compose Multiplatform 在安卓 + macOS 的空壳，含窗口尺寸类与折叠形态（Builder-C）。
3. Spike B：公式渲染（KaTeX in WebView）+ Markdown 流式渲染，在安卓和桌面（Builder-C，Scout 先调研库）。
4. Spike C：Ktor 服务端经订阅桥做 Claude 真流式 + 兜底，端到端首字时延（Builder）。
5. Spike D：SQLite 事件账本 + 投影（掌握度、复习队列）+ 用 StudyCoach 的规则做属性测试（Builder）。
6. 领域规格：把 StudyCoach 的证据策略、复习调度、阶段、日记规则整理成一份不依赖其代码的规格，并标注与 DeepTutor 行为的差异（Architect / Scout）。
7. 设计系统：StudyCoach 令牌 → Compose 主题与组件清单（Draft 出稿，Builder-C 落地）。
8. 迁移规格：DeepTutor → Coach 的数据映射（Builder，只读 DeepTutor 的库）。

## 七、风险

1. **工作量**：从 0 做一个双端应用，是“月”级别；StudyCoach 的前车之鉴是范围蔓延和治理过重。对策：M1 严格只做闭环；不设数字门禁。
2. **额度**：Claude 订阅也供你本人使用；工程主力放 Codex，Claude 只管判断与验收；Sage/Expert 只点名。你可以设一个周额度上限。
3. **公式渲染 / 流式 Markdown** 在 Compose 里不成熟，是 M0 要先证伪或证实的。
4. **Mac 在线率**：服务端在这台 Mac 上，它休眠，手机就连不上（你的 Mac 小时在线率只有 11–38%）。要想“随时能学”，要么让 Mac 不休眠，要么把服务端搬到常驻机器（需要把订阅登录放过去，属于“第三方账户/权限变更”，要你拍板）。
5. **不干扰期中**：DeepTutor 保持原样直到 11-02。

## 八、成功的样子（可度量）

- M1：连续 7 天，你只用 Coach 完成当天学习，不回头打开 DeepTutor；打开 App 到开始学习 ≤3 次点按。
- 导师回答首字 ≤5 秒（流式）；一次完整“学-练-批”循环里你不需要手选任何资源。
- 所有掌握度变化都能在界面里下钻到原题、原答和判分依据。
