## 重讲首字耗时：定位与修复

测量口径：客户端 `CoachTtft`（点「换个例子再讲」到首个可见字），模拟器，同一桥、同一模型，A（改前 `5b22740`）与 B（改后）两个隔离服务交替运行，各用生产库同一份只读拷贝，每轮清应用数据后重新配对，先讲一遍再答错再重讲（真实顺序）。

拆耗时：排队约 0.1–0.3 ms；客户端首字减去桥首字约 0.02–0.22 秒（点按到服务端、转发、回传）；桥首字占全部。再拆桥首字：直接跑同一订阅 CLI，约 1.1 秒是 CLI 启动、读入输入和出第一个字，超出的 3–6 秒全是模型输出前的思考块（`content_block_start: thinking`）。输入 token 多不是主因：同一请求在 1.9 万 token 和 4.7k token 下首字相近，是否进入思考才决定快慢。

触发思考的两个因素（同一请求回放，每格 n=4–6）：请求里有教材页，且结尾写着「只能依据教材回答」，模型要先对照教材核实；三道带计算的错题加长上下文更甚。把教材页去掉但保留这句话，反而更慢（5–8 秒）；只改这句话、仍带 1.1 万字教材，仍 4.7 秒；两者都改，约 1.2–1.5 秒。

修复：带错题的重讲，(1) 推理强度降为 `low`；(2) 每道错题都有已复核解析时只带知识点标题和出处，不带教材页，并把结尾改成「已复核解析就是依据」；(3) 有错题缺解析时仍带最多 4000 字的最相关教材页，并保留原措辞；(4) 近期对话每条截到 800 字；(5) 指令要求以「你选的」开头、不要先规划。其他请求不变，仍为 `medium`。

结果（n=6 个知识点交替，秒）：改前 5.62、5.99、7.50、7.50、7.71、8.63，中位 7.50，p90 8.63；改后 1.58、3.82、1.23、1.33、1.28、1.61，中位 1.46，p90 3.82。桥侧输入 token：改前约 1.5–2.0 万，改后约 4.7–5.9k。改后 6 次首段全部以「你选的……不对，因为……」开头并说明正确项为何成立，再换例；与改前一样只覆盖三道错题中的第 1 道。取舍：已复核解析存在时，换例所用知识来自解析和模型自身，不再逐页对照教材，示例数字未逐项验算。
