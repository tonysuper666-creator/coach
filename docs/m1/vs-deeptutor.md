## 口径

频次只数用户回合。一条保留下来的精通会话，54 条用户消息，2026-10-28T18:31:56Z 至 2026-10-29T21:20:14Z。更早的模型调用原文已经不在会话库里，不计数。分类只用 `tools/corpus/prepare-replay.py` 的 `intent()`，不把没匹配上的自由发言再并进「问概念」。工具调用次数和自然日不进频次列。

三种时间分开写：

- 端到端：从点击或启动命令发出之前开始计。强制停止是准备，不进这只钟。先做界面转储，转储确认目标文字之后才截图。上界是这张成功截图的完成时刻，不是截图命令的开始时刻。目标在上一张转储开始时还不在、在成功截图完成时已经在，出现时刻就落在这个开区间到闭区间里。第一张转储已经命中时，只有上界，没有缺席帧。两个上界不能相减，也不能写成「至少快若干秒」。写动作没有在他的 DeepTutor 账号上重做。
- 后台：冻结快照上的时间戳。回合墙钟是 `turns.finished_at - turns.created_at`，只含已完成、且消息元数据里带了该回合 id 的行。工具出现时间是该回合里该工具第一次 `tool_result` 减去回合 `created_at`。请求到首字是该回合里 `llm_calls` 的 `started_at + ttft_seconds` 的最小值，再减去回合 `created_at`，只连接冻结快照里的回合 id。中位数用两个中间值的平均（偶数个时）；p90 用 nearest rank，`sorted[ceil(n*0.9)-1]`。
- 推算：这一轮没有用推算填秒数。

Coach 隔离桥上的毫秒和上面的「请求到首字」不是同一段。桥日志里的 `ttft` 从模型进程拿到请求起算，`queue` 是排队，`total` 从请求进入桥起算到完成。请求到首字写成 `queue + ttft`。手机上看到文字的时间单独写，不拿去减后台秒数。

比较规则：两侧都有同一种端到端区间，才分更好、持平、不如。较慢一侧的缺席下界已经晚于较快一侧的成功上界，并且这个下界大于较快上界的 1.2 倍，较快的一侧才记更好；下界不超过 1.2 倍、区间重叠、或者任一侧没有缺席帧，都记待验证，不记持平。只有一侧有端到端，记待验证。页面本身不存在，记缺。一次现场样本不和历史中位数比出更好。

Coach 的讲解池是另一次冻结：测试库里 `task=TEACH` 且 `status=complete` 的 46 行，首字中位 4439.5 毫秒、p90 8314 毫秒，整轮中位 7232.5 毫秒、p90 11316 毫秒。这是一整池，不能拆给「提问」或「接着学」。账本里提交到判分的差是 0 毫秒的那些行，是同一条记录，不是屏幕上看到对错的时间。

题库有两份，不要混：教学调用那份快照是 33 题、5/49 个知识点；拿去开隔离服务端的生产库副本是 40 题、6/49 个知识点。

复算请对着冻结快照跑，不要查活库，也不要查这次手机实测写过的那份运行副本。材料核查的三个数在这份快照上是：`intent()` 为 answer 28 / unknown 20 / question 3 / continue 2 / request_batch 1；`mastery_grade` 中位 28.415 秒（p90 42.432，n=28）；`read_source` 中位 19.536 秒（p90 24.905，n=3）。±20% 只对这些冻结中位数。它不代替验收。验收仍是这 8 到 10 个动作的双侧测量，加上从对照表里随机抽 3 行再测一遍。单次新调用、单张手机截图，以及「落在 p90 里」，都不是 ±20% 的标准。
